# LastKey

A dead-man's-switch inheritance vault for your crypto. Prove of life is your own wallet activity: check in before your timer runs out and nothing happens. Miss it, and your beneficiaries can claim their shares with a passphrase only they hold.

## Live demo

A local demo chain (chain id 31338) runs the full flow: deploy, register, check in, edit the vault live, and claim. The frontend is phone-first and connects through the Reown WalletConnect modal (SubWallet, MetaMask, or any WalletConnect wallet).

## How it works

- Register a vault with a check-in interval (1-3650 days) and grace window, encrypted instructions, and beneficiaries with percentage shares.
- Prove of life by checking in, or just by transacting: wallet activity counts as a heartbeat, not only the button.
- Miss the deadline and the grace window, and claims open. Each beneficiary connects their wallet, and their non-transferable (soulbound) claim ticket is detected automatically.
- Claims require the passphrase the owner shared. It never lives on-chain in plaintext.

## Two claim modes

- Specific assets: the beneficiary sweeps only ERC-20 tokens the owner explicitly listed, within caps.
- Everything: the owner records a blanket-approval attestation on-chain and approves the vault for their tokens; a keeper sweeps everything approved and held, including tokens never listed.

The owner can switch modes while alive; the mode locks at claim time.

## Edit, don't restart

`updateVault` edits a live vault in place, same epoch: interval, grace, beneficiaries, shares, passphrase and instructions. The clock does not reset. Shorten 30 days to 7 and the time already elapsed still counts.

## Shamir passphrase split (v3.1)

Passphrase recovery without trusting a central party:

- The owner can split the secret into encrypted Shamir shards at registration (setShardSplit).
- A k-of-n threshold (e.g. 2 of 3 heirs) is set on-chain.
- Each beneficiary can read ONLY their own encrypted shard off-chain via shardOf(owner).
- If the owner dies without ever telling the heirs the passphrase, k beneficiaries combine their shards to reconstruct it and claim.
- No single beneficiary can steal early; no heir is locked out if the owner dies suddenly.

## Automatic activity heartbeat

`npm run watch:activity` runs a polling service that detects successful outgoing transactions from wallets with explicit signed authorization and calls the configured LastKey contract's `watcherCheckIn(owner)`. It tracks only the declared wallets, on the declared chain and contract, and only counts successful outgoing EVM transactions. It does not use or request an owner's seed/private key, does not infer other activity, and never signs for tracked wallets.

Configuration is via environment variables: `RPC_URL`, `CHAIN_ID`, `LASTKEY_ADDRESS`, `WATCHER_PRIVATE_KEY` (dedicated watcher account only), and `WATCH_AUTHORIZATIONS` (path to JSON array). Optional: `WATCH_STATE_FILE`, `POLL_MS`, and `CONFIRMATIONS`. State is written locally to the state file. Use persistent encrypted storage and a process supervisor for hosted use. Add the watcher account address to the contract with the admin's `setWatcher` action before starting; it needs native gas for its own check-in transactions.

To grant consent, the tracked wallet signs the exact message generated by `authorizationMessage` in `keeper/lib/activity-watcher.js`. The signed authorization binds the chain, LastKey contract, vault owner, tracked wallet, activity definition, and expiry. Store entries as `{ "chainId": "...", "lastKey": "0x...", "owner": "0x...", "wallet": "0x...", "expiresAt": "...", "signature": "0x..." }`. Do not place secrets or private keys in that file. Rotate/revoke consent by removing the authorization and restarting the service. The service is a single-process poller; production use requires monitored uptime, persistent state, adequate RPC limits, and operational key management. A watcher cannot guarantee heartbeat if the process or RPC is down.

## End-to-end cross-chain claims

The destination `LastKeyBridgeReceiver` already enforces a configurable watcher quorum, chain-and-contract-bound signatures, beneficiary binding, short expiry, single-use nonces, replay prevention, a funded mirror, and the source claim time. `keeper/lib/crosschain.js` now provides a source-state-verified package builder and beneficiary-side submission helper. It re-reads source vault state, checks claim window and roster, validates destination receiver code and mirror funding, and signs the exact receiver domain. The beneficiary submits their own secret and transaction; the secret is not sent to the watcher helper.

Minimal integration shape:

```js
const { prepareCrossChainClaim, submitCrossChainClaim } = require("./keeper/lib/crosschain");
const pkg = await prepareCrossChainClaim({ sourceProvider, destinationProvider, srcChainId, srcVault, owner, beneficiary, receiverAddress, watcherWallets });
const receipt = await submitCrossChainClaim({ destinationSigner: beneficiarySigner, receiverAddress, claimPackage: pkg, secret });
```

This is a quorum-attested mirrored escrow, not a trustless native bridge: destination does not independently verify source state. The test suite exercises the source read, quorum signing, destination submission, beneficiary restriction, replay controls, and contract-level protections. Real use still requires independent watcher operators and signer custody, deployment of source and destination contracts, funded destination mirrors, RPCs, and an operational relay/API to collect and return quorum attestations. No live bridge, validator set, or relayer is bundled or claimed here.

## Threat model and honest assumptions

1. Liveness oracle vs stolen phone: LastKey uses authorized wallet transactions and an active check-in button as proof of life. If an attacker gains full access to the owner's phone or signer pre-death, they can keep checking in. We do not use third-party death certificates or centralized oracles because they reintroduce custody and KYC; LastKey trades edge-case phone theft for sovereign, oracle-free execution.
2. Cross-chain watcher trust: the cross-chain claim receiver relies on a quorum of watcher signatures. In production, watcher operators must be independent to prevent collusion. The destination chain cannot independently verify the source chain with the current EVM contracts.

## Structure

- `contracts/LastKey.sol` - the vault, tickets and sweep system
- `contracts/LastKeyBridgeReceiver.sol` - cross-chain mirrored-escrow receiver
- `frontend/` - phone-first dapp (no build step)
- `keeper/` - claim/sweep automation, activity watcher, and cross-chain helpers
- `notify/` - webhook event service
- `test/` - hardhat tests
